AQU-MR Simple Project Build Specification Adaptive Query Understanding and Modality-Aware Retrieval for Multimodal Document Question Answering Dataset: VLR-CVC/DocVQA-2026 1. Project Goal Build a simple, reliable multimodal RAG system that accepts a  document and a natural-language question, understands what information is needed, retrieves relevant evidence from text, tables and images, and produces a grounded answer with source-page provenance. The system must generalize to unseen questions and documents. No document-specific, page-specific or question-specific hardcoding is allowed. 2. Scope Use only three modalities: Text Tables Images Maps, comics, business reports, science papers, slides and other document types are handled through these three modalities. Do not build separate reasoning systems for individual document categories. 3. Simple Architecture Document → Ingestion → Text / Tables / Images Question → Query Understanding Query Understanding → Text + Table + Image Retrieval Retrieval → Page-Level Fusion Fused Results → Evidence Builder Evidence + Question → Answer Selection Selected Evidence → Grounded LLM/VLM Generated Answer → Validation Validated Answer → Answer + Source Pages 4. Dataset and Ingestion DocVQA-2026 benchmark documents are image-first. Do not assume that benchmark documents contain a PDF text layer. Use OCR and image processing on page images. Support two ingestion paths: from_docvqa_images(doc_id, page_images) for the benchmark. from_pdf(path) for optional user-uploaded PDFs. Both paths must produce the same downstream representation. Every item must retain document_id, page, modality, content, source and metadata. 5. Text Processing Extract OCR text from benchmark pages. Keep raw OCR separately from cleaned text. Apply  only conservative cleanup such as repeated whitespace and obvious extraction artifacts. Preserve page provenance. Use meaningful chunks rather than tiny fragments. 6. Table Processing Tables are a first-class modality. Preserve headers, rows, columns and cells. Do not flatten tables and lose their relationships. If structured table extraction is unreliable, keep the original page image and OCR as authoritative evidence instead of inventing a table structure. 7. Image Processing Keep the original page image and create image embeddings. Image retrieval must use both visual similarity and OCR/page-text signals; CLIP alone is not sufficient. 8. Query Understanding Before retrieval, derive a small query contract: Intent: FACT / TABLE_LOOKUP / VISUAL / COMPARISON / LIST / SUMMARY Modality confidence: text / table / image Important entities and terms Expected answer type Optional period, relationship or comparison requirement Routing must be soft. A question can retrieve from multiple modalities. 9. Retrieval Text Use BM25 plus dense sentence embeddings and retain document/page/chunk provenance. Tables Retrieve structured tables using lexical and dense representations while preserving the original table. Images Retrieve image candidates using  CLIP/image-text similarity and OCR/page-text retrieval. Retrieve candidates from both signals, take their union, then fuse them. Page-Level Fusion Combine text, table and image scores with simple configurable weights. Do not discard pages with arbitrary score thresholds. 10. Evidence Builder Keep evidence separated by page and modality. Do not create one large unstructured text block. Page number Relevant text blocks Complete relevant tables with headers and row/column relationships Relevant page  images Source metadata Use a reasonable evidence budget. Do not pass every page to the model and do not use a tiny fixed window that can cut out the answer. 11. Answer Selection Retrieval answers WHERE the information is. Answer selection determines WHAT information actually answers the question. Build an answer contract dynamically from the question and compare evidence candidates against it. For table answers preserve table_id, page, row, column and cell value. Never select a value merely because it is first, numerically similar or has the highest keyword overlap. 12. Grounded Answer Generation Give the generator only the question, query contract and selected evidence. It must answer only from supplied evidence. Answer the exact question. Do not summarize unrelated evidence. Preserve exact values, units, names and dates. Respect table row/column relationships. Use supplied images for visual questions. Do not use outside knowledge. Do not invent unsupported facts. 13. Answer Validation Validate the final answer for question relevance, entity support, numerical/value support, unit and period support, table row/column support, image support, provenance and unsupported claims. If a valid evidence-backed candidate exists, do not incorrectly abstain. If validation fails, regenerate once with stricter grounding; if it still fails, return a controlled insufficient-evidence response. 14. CPU-Friendly Components Component Choice Text embeddings all-MiniLM-L6-v2 Text retrieval BM25 + FAISS Image retrieval CLIP + OCR/page-text OCR Tesseract Vector search faiss-cpu Generation API-based vision-capable LLM if local CPU-only Web UI Streamlit 16. Evaluation Keep  retrieval and QA evaluation separate. QA: Exact Match, ANLS where appropriate, answer accuracy, unsupported-claim rate, correct-abstention rate. Report results by text, table, image and multimodal questions where the data supports it. Report  Recall@K/MRR only when independent page-level ground truth exists. Never derive gold pages from the retriever. Use official DocVQA answers for QA evaluation and respect train/validation/test separation. 17. Development Order Inspect the actual DocVQA-2026 files and annotations. Implement ingestion and verify page images/OCR. Implement text retrieval and test independently. Implement table retrieval and test independently. Implement image + OCR retrieval and test independently. Implement query understanding and soft modality fusion. Implement evidence building. Implement answer selection. Implement grounded generation. Implement validation. Run evaluation. Add the simple Streamlit interface. 18. Debug Mode Provide --debug output containing: Question and query analysis Top text/table/image results Final page ranking Selected evidence Answer contract Selected candidate Raw model answer Validation result Final answer and source pages 19. Streamlit Interface Upload document Process/index document Enter  question Show answer Show source pages Show selected evidence Optional debug view 20. Rules No question-specific hardcoding. No document-specific or page-specific overrides. Do not modify retrieval to hide a generation problem. Do not modify generation to hide a retrieval problem. Do not flatten tables and lose structure. Do not rely on CLIP alone for image retrieval. Do not let the generator use outside knowledge. Do not claim page-retrieval metrics without independent ground truth. Keep the system simple and independently testable. 21. Final Acceptance Criteria Text-heavy documents retrieve relevant evidence and answer correctly. Table questions preserve and select the correct row/column/cell. Image-heavy documents retrieve relevant pages using  visual + OCR signals. Mixed questions can combine modalities. Answers are grounded in selected evidence. Unsupported claims are rejected or corrected. Source pages are traceable. Known and unseen questions work without hardcoded rules. The evaluation workflow is reproducible. The Streamlit upload-and-question workflow works. 22. Research Contribution The project demonstrates how adaptive query understanding can determine which document modalities are most useful, while lightweight multimodal  retrieval combines text, table and image evidence to produce grounded answers.
